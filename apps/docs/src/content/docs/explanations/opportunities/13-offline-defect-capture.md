---
title: Keeping defect reports when workshop devices lose their connection
description: Locally saved observations and deliberate conflict handling can prevent lost reports without allowing offline vehicle releases.
---

A technician inspecting a vehicle notices a defect and starts recording it on a workshop device. The connection drops before the form reaches the server. If the screen does not clearly distinguish a saved report from an attempted submission, the technician may leave believing that another shift can see the observation. Alternatively, they may copy the details onto paper and enter them again later. This illustrative situation creates a gap between discovering a fault and making that knowledge available to the people who need it.

The proposal is to make a defect observation durable on the device before trying to send it. A visible local-save receipt would tell the technician that the report survived on that device, while a separate confirmation would show when the server received it. The distinction matters because local storage does not make the report available to a controller or another technician. The user must be able to see which reports still need a connection and take the established escalation route when an observation requires immediate attention.

Connection loss is a hypothesis to investigate, not an observed fault in the supplied LionLink application. The fictional workshop records contain vehicle and work-order references, fault summaries, update times, work status, and release status. They do not contain device identities, delayed submissions, or evidence of abandoned forms. The [workshop findings](/docs/workshop-findings/) also distinguish expected completion from confirmed Engineering release. That distinction gives the project an important boundary. A technician can preserve an observation offline, but the device cannot independently declare a vehicle released for use.

The core mechanism is a durable local queue, meaning a list of saved operations that remains on the device until the server acknowledges them. Each observation receives a unique identifier when it is created. When the connection returns, the device sends that identifier with the report. If a request times out, the device can retry the same operation. The server recognizes the identifier and records the observation once, even if it receives the request repeatedly. This avoids forcing the technician to decide whether an ambiguous timeout means they should submit a second report.

Consider an illustrative handover between two technicians. The first records a damaged fitting while disconnected and restarts the device before reconnecting. The report remains in the local queue. Meanwhile, a second technician adds a different observation to the same work order from an online device. When the first reconnects, both observations can coexist because neither replaces the other. If both technicians instead correct the same existing fault description, the system should preserve both versions and ask an authorized person to resolve the disagreement. Automatically keeping whichever message arrives last could discard the more accurate observation simply because its device reconnected earlier.

To support that distinction, every correction records the server version the technician had seen. The server can accept a correction when that version is still current or identify a conflict when someone else has changed it. Device timestamps remain useful descriptions of reported capture time, but they cannot settle the conflict because device clocks may disagree. Photographs also need their own upload status. A large attachment that fails to upload must not make a saved text observation disappear. Staff should see that the text has synchronized while the image is pending, with an option to retry or escalate through an approved alternative.

A paper form may still be the right response to rare connection failures. It is familiar, works without battery power, and can fit an existing handover process. The justification for software is stronger if research finds repeated delayed entry, duplicate reports, or uncertainty about whether observations reached the right person. Adding an offline queue is not a small checkbox on an existing form. It introduces device storage, retries, conflicting edits, and a second place where sensitive workshop information remains. Those costs should be accepted because a measured reporting problem warrants them, not because offline support sounds generally useful.

The first implementation should cover observations on existing work orders, with text and a limited attachment capability. It should exclude offline release decisions and changes to dispatch authority. Engineering would define which fields are additive observations and which corrections require review. The application team would provide local persistence, retry handling, server acknowledgements, and the conflict screen. Device support staff would identify supported hardware, storage limits, and restart behaviour. The integration must preserve the existing work-order identifier so that delayed evidence arrives at the correct job. If that job has closed or the vehicle has returned to use, a new safety-relevant observation must alert the designated Engineering duty reviewer for acknowledgement and assessment. Historical filing alone is insufficient. Engineering must define that escalation rule and who covers an unacknowledged alert. The reviewer decides the operational response through the existing authority process.

Failure behaviour needs to be explicit at the moment of capture. If storage is full or unavailable, the device must say that it has not saved the observation and direct the technician to the existing reporting method. A device that is lost before synchronization may take its local-only reports with it, so the service must not promise recovery it cannot provide. Access revocation also cannot immediately erase information on a disconnected device. LionLink would need managed-device protection, a bounded retention policy, and restrictions on unnecessary personal information. Once acknowledged, local copies can be removed according to that policy without deleting the server record.

Adoption should start with technicians who actually work in the affected locations. They need to understand the difference between saved locally, received by the server, and awaiting conflict review without interpreting technical error codes. A supervisor must own the unresolved-conflict queue and have time to resolve it. Ongoing maintenance includes testing storage behaviour after device or browser updates and checking that work-order changes do not break synchronization. If the workflow creates a growing backlog of unresolved reports, that is an operational failure even when no bytes are lost.

The pilot should combine deliberate failure tests with observed workshop use. Test a disconnected save followed by a restart, repeated delivery of the same operation, conflicting edits from two devices, and storage exhaustion. Verify the actual server records rather than relying on the device's success message. In use, compare reporting completion, duplicate entry, time until observations reach the server, and supervisor effort with the current process. Safety-relevant observations that remain unnoticed should be examined individually rather than hidden inside an average synchronization time.

The immediate recommendation is a short workflow and connectivity investigation before building. If technicians already report reliably through a suitable paper fallback, a clearer form status may be enough. If the investigation confirms lost or repeatedly re-entered observations, fund the bounded offline capture workflow with explicit ownership of conflicts and device support. Its value is preserving evidence through connection failures while keeping the authority to release a vehicle in the established online process.
