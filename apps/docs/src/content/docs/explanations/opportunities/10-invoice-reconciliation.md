---
title: Checking that repair invoices match approved and completed work
description: How evidence-linked line checks could help finance resolve duplicate, unsupported, or partially delivered repair charges before approval.
---

A repair invoice looks plausible when read alone. The supplier name is familiar, the total is within the range expected for the job, and the bus has returned from the workshop. The invoice may still include a diagnostic fee already covered by another charge, a part that was ordered but never received, or work outside the approved scope. This proposal would help LionLink's finance reviewer connect each billed line to the work that was authorized and the goods or services actually received, leaving clear exceptions for human resolution.

The fictional exercise contains repair actions and combined labour and parts charges. Some condition-check notes describe work included in a linked job, and the cost proposals state commercial scope and exclusions. The [cost comparison explanation](/docs/cost-findings/) makes an important distinction: a quoted package is neither an approved purchase nor evidence that work was completed. Those records motivate a reconciliation question, but the repository has no invoice scans, purchase-order line ledger, or delivery receipts. It therefore cannot demonstrate overbilling, an existing control failure, or a recoverable amount. The business case requires examining the real finance workflow before estimating value.

A reviewer can already compare documents manually, and an existing finance system may perform the necessary checks for structured purchases. The opportunity lies where repair evidence arrives in inconsistent documents and reviewers spend substantial time assembling it. Searching invoice text would help locate a phrase, but would not establish whether the charge is supported. The proposed mechanism combines document extraction with explicit matching rules. It should make the evidence easier to inspect while refusing to reconcile a line that lacks a reliable connection to an approved order and a receipt or completion acknowledgement.

Document extraction converts an invoice line into fields such as supplier, order reference, item, quantity, unit price, currency, and amount. Each extracted field must retain its source page and location so the reviewer can inspect it. The matching stage then connects that line to the relevant approved order line and the received quantity or completed service. Arithmetic checks compare quantities, prices, and totals under the organization's agreed rules. A separate duplicate check looks for the same charge already recorded. Uncertain text or identity matches remain unresolved rather than becoming accepted because the total happens to look reasonable.

Consider an illustrative order for two identical parts at one hundred dollars each, with a receipt confirming that only one arrived. If an invoice bills both, the system can support one hundred dollars of received quantity and flag the remaining hundred for clarification, subject to the agreed payment terms. These figures explain the method and are not LionLink transactions. If the same packet also includes a diagnostic fee described as included in another approved line, the reviewer sees that scope conflict alongside the source wording. The system does not decide that every repeated description is a duplicate. Two legitimate visits can have similar descriptions and require distinct evidence.

The separation between extraction and matching matters. If the invoice image says ten units and extraction reads one, otherwise correct reconciliation rules may produce a convincing wrong result. The prototype must therefore measure both stages independently. Low-confidence fields should require review before they support a reconciled line. A model may help read varied document layouts, but approved prices, received quantities, and duplicate rules should be calculated explicitly. Text inside an attachment remains document content even if it contains instructions addressed to an automated assistant. It cannot change the system's approval rules.

The first deliverable should be a review packet for one work order, initially using clearly labelled synthetic documents because the fixture lacks the required originals. The packet should include an approved order, a completed-work or goods receipt, and an invoice. Deliberate cases should cover a valid partial delivery, a duplicate charge, a missing receipt, and an uncertain item description. A finance reviewer should be able to see why each line is supported or unresolved and correct a proposed match. The prototype should end at a draft review outcome. It must not execute payment or alter supplier bank details.

Before a live pilot, finance needs to define the authoritative order and receipt sources, line identifiers, approved tolerances, tax treatment, currencies, units, and handling of credit notes. Engineering or workshop staff must clarify what counts as acknowledgement of a completed repair service. A closed work order may establish that a job ended without proving that every invoiced part was fitted or received. Supplier aliases and part descriptions need controlled matching rather than guesswork based on similar words. These agreements determine whether the tool can make a trustworthy connection, and they may reveal a record-keeping problem that should be solved before automation.

The finance-system owner should manage access, retention, and the route by which draft results enter the existing approval workflow. Supplier attachments and payment-related information require the same controls as their current records. Reviewers need an explicit way to mark a genuine exception, request missing evidence, or reject a proposed match. If a document changes or a credit note arrives, the prior result must be revised rather than treated as permanently reconciled. If extraction fails or an integration is unavailable, the invoice should remain available for manual processing with a clear account of which checks did not run.

Adoption should focus on reviewer effort and trust. A tool that flags every line creates another queue rather than reducing work. Conversely, a tool that silently accepts weak matches can conceal incorrect payment. The pilot should compare independently labelled invoice packets with the tool's results, recording false reconciliations separately from unresolved valid lines. It should measure time spent collecting evidence, correcting extraction, and completing review, not only time spent in the new interface. Confirmed exceptions can demonstrate useful detection, but a flagged amount is not automatically a saving. Finance must establish whether the charge would otherwise have been paid and how it was resolved.

LionLink should first ask finance to select representative repair packets and assess whether the required approval and receipt evidence exists. If the existing purchasing system already performs these checks reliably, configuring that system may be the best solution. If evidence is fragmented but recoverable and repeated manual matching consumes material effort, the bounded review prototype has a clear justification. Further implementation should depend on precise supported matches and a lower total review burden. Where receipts or approved scope are routinely missing, improving those records is the necessary investment before automating invoice reconciliation.
