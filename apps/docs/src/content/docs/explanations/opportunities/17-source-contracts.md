---
title: Stopping a data refresh from silently changing a report's meaning
description: Agreed source rules and quarantine can keep incompatible datasets out of published LionLink reports.
---

A maintainer replaces an old operating extract with a new file. The import succeeds, the report loads, and the figures look plausible. Yet the new file covers an entire day while the old one covered a morning window. A comparison that appears to show increased boardings now compares different periods. This illustrative failure is difficult to notice because nothing has crashed. The software has accepted the file's shape without checking whether its meaning still matches the report.

LionLink could prevent this class of failure through source contracts. A source contract is a written, machine-checkable agreement about what a dataset contains and how consumers may interpret it. It includes field names and types, but also units, coverage, identifiers, and relationships between tables. A candidate refresh would remain separate from published data until it passes those checks. If it fails, the system would retain the last accepted version and explain the specific disagreement to the maintainer and source owner.

The repository already shows why meaning must accompany values. The [measures and coverage guide](/docs/measures/) distinguishes boarding events from individual people and defines the bounded morning operating extract. Calendar records include time zones, queue observations include scope and observation boundaries, and timetable records carry versions and effective dates. The [record-tracing guide](/docs/explore-records/) helps readers connect findings to underlying records. These details are part of the evidence, not optional annotations. The current materials do not prove that a refresh has corrupted a report. They identify promises that a future refresh process should preserve or change explicitly.

The proposed admission process begins in a staging location, which is a storage area that published reports do not read. The importer identifies the source and contract version, checks required fields and units, and verifies that related identifiers exist. For example, a stop call that references an unknown trip cannot become part of an accepted version. The process also checks declared coverage against the contract. It then produces a manifest, meaning a record of the files, source identity, retrieval time, and checks associated with the candidate. A content hash, a calculated fingerprint of a file's bytes, helps detect later changes to those exact files.

In the illustrative morning-to-all-day refresh, the candidate's declared observation window conflicts with the current contract. The system quarantines the candidate, meaning it keeps the files for investigation but does not publish them. The report continues to use the last accepted dataset and displays its existing coverage and age. The maintainer sees that the failure concerns the observation window rather than malformed rows. If the broader coverage is intentional, the source owner and report owner agree a new contract version and review affected comparisons before publishing it. An intentional change should have a supported path rather than require someone to bypass validation.

Publication must replace the dataset as a whole. If a new trip table becomes visible before its matching stop-call table, users can receive results assembled from incompatible versions even when both files pass individually. The accepted version should therefore become active in one controlled change after all checks succeed. Reports should identify which version they used, and rollback should restore a previously accepted complete version. This is a data-management mechanism that changes what the application can read, rather than a warning that users must notice after an incompatible refresh is already live.

The approach has a firm limit. Code cannot detect an undeclared change that leaves every observable field looking valid. If a supplier silently changes a distance unit but provides no unit metadata, the importer may have no reliable basis for deciding what happened. Broad plausibility checks can prompt investigation, but they cannot establish the correct unit. A hash proves that bytes are unchanged, not that the source is truthful. Source-owner agreements and maintained metadata are therefore prerequisites. Stronger validation code cannot substitute for a source that communicates changes poorly.

A manual review may be enough for a rarely refreshed report with one knowledgeable maintainer. Existing database constraints can also catch duplicate keys and missing references without a new framework. Custom admission tooling is justified when refreshes recur, several tables must remain consistent, and semantic assumptions affect decisions. The first implementation should focus on one operating extract and its actual consumers. It should not attempt to define a universal contract language for every future LionLink dataset. A small versioned specification and a rerunnable validator can establish value before wider adoption.

The bounded deliverable would include the contract, isolated candidate storage, validation diagnostics, a version manifest, controlled activation, and rollback. The source owner would confirm units and coverage. Report owners would identify assumptions that must remain stable. Engineers would connect activation to the application's dataset reader and make rejection reasons understandable. An operational owner would monitor failed refreshes and decide whether the response is a corrected file, an intentional migration, or continued use of older data. The age of the accepted dataset must remain visible so that successful quarantine does not hide growing staleness.

Adoption requires a practical change process. If every legitimate source improvement causes an unexplained failure, staff will be tempted to disable the checks. A reviewed contract update should state which meaning changed and which consumers need adjustment. Urgent corrections should use the same traceable activation process, with an identified approver. Rejected candidates need retention limits and appropriate access because staging can accumulate sensitive source data in a future production setting. Ongoing costs include maintaining the contract as sources evolve and keeping diagnostic messages useful to staff who did not write the validator.

The proposal can be tested without live data by deliberately changing a small fictional extract. Introduce a duplicate call identifier, an unknown trip reference, a missing time zone, and a different observation window. Each should fail for the intended reason, while a valid candidate should activate without mixed table versions. A rollback test should demonstrate the report reading the earlier accepted version. Operational evaluation should then compare refresh investigation effort, rejected genuine errors, unnecessary rejections, and time spent on old data. Counting every rejected file as a benefit would exaggerate value if most rejections are harmless changes handled badly.

LionLink should prioritize the source agreement before the software if units and population boundaries are not already explicit. Once those promises exist, a narrow admission process is a defensible investment for reports that influence operational or spending decisions. The sponsor's next choice is one feed and one report whose meaning must survive refreshes. If the validator can protect that relationship without creating unmanageable delays, expansion is justified. If the source cannot declare its meaning reliably, the immediate remedy is better source governance rather than a larger validation system.
