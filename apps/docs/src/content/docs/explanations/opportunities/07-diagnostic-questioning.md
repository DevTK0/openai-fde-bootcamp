---
title: Choosing the next useful test when a bus fault has several possible causes
description: How an engineer-approved sequence of diagnostic questions could reduce unhelpful testing without guessing a repair.
---

A passenger reports a warm saloon, and the bus reaches the workshop with several possible explanations. The report describes an experience, not a confirmed failed part. A mechanic can follow a standard checklist, repeat a familiar test, or begin with the cause that seems most likely. The proposed project would help choose the next approved observation that best distinguishes the remaining causes, then adjust the sequence when the mechanic records the result. The intended benefit is less unnecessary diagnostic work while preserving Engineering's responsibility for the diagnosis and repair.

LionLink's fictional work orders connect reported symptoms, inspection findings, fault families, and repair actions. One selected warm-saloon record links the complaint to a recorded hose leak. The [passenger findings](/docs/passenger-findings/) explain why an account of discomfort does not itself establish a mechanical cause. That distinction is the starting point for this proposal. The example demonstrates that symptom and finding are different kinds of evidence. It does not establish that warm-saloon reports generally indicate a hose leak, or that the supplied repair records are sufficient to calculate the probability of each possible cause.

A fixed checklist has important strengths. It is familiar, reviewable, and can enforce necessary checks in a safe order. LionLink should not replace it merely to make the experience feel more intelligent. The opportunity exists where engineers can identify branches that depend on prior findings and where a fixed sequence regularly spends time on tests that no longer help. The proposed system would preserve mandatory steps and select among optional approved tests. If a short existing decision tree already covers the fault reliably, improving that tree may be the whole project.

To choose a test, the system needs a small set of plausible causes and an approved inventory of observations. For each observation, engineers describe its possible outcomes, prerequisites, approximate effort, and how each outcome would change the assessment of the causes. The software estimates how much uncertainty each permitted test is likely to remove and compares that with its effort. This is often called information gain. In everyday terms, a test is useful when its possible answers send the investigation down meaningfully different paths. A test that returns the same result for every remaining cause adds little diagnostic value.

Consider a deliberately simplified example approved for a prototype, not an actual maintenance instruction. Suppose the current evidence leaves two broad explanations, a problem with air delivery or a problem with cooling performance. One approved observation distinguishes those groups, while another records a symptom that both groups commonly produce. The first observation is more useful at that point even if the second is familiar. After the mechanic enters the outcome, the system narrows the remaining explanations and chooses the next permitted observation. If the result fits neither group, it should reopen the unknown-cause path rather than force the case into the original choices.

The interface should make that reasoning visible without requiring the mechanic to understand probability notation. It should explain why a question is useful now, show the approved procedure reference, and state what a positive, negative, or inconclusive result would change. The mechanic records the actual result before the tool continues. It should never infer that a test was passed because the mechanic skipped a field or because a repair was later recorded. An override with a reason can be valuable evidence that the proposed sequence missed local context. It must not silently become proof that the recommendation was correct.

This approach depends on information absent from the exercise. The work orders contain selected findings and repairs, but not a complete record of negative tests, test durations, or the relative frequency of alternative causes. Successful repairs alone can bias the system toward the causes that were documented. Engineering must create and review the initial cause catalogue, test inventory, and safety prerequisites. Estimates of how likely each outcome is may begin as explicit expert assumptions for staged evaluation. They should not be presented as measured probabilities. If reasonable expert estimates produce wildly different test orders, the project needs better observations before live recommendations.

The first implementation should cover one non-emergency comfort complaint with a small engineer-approved set of causes and tests. A fixed question inventory is preferable to automatically generated instructions because it isolates the value of selecting the next test. A language model might later help map varied symptom wording to the approved vocabulary, but it must not invent procedures or diagnosis evidence. The initial tool should run on staged cases with known causes, plus ambiguous cases that require escalation. It should not order parts, close work orders, or release a vehicle.

Safety constraints must apply before the ranking calculation. A highly informative test is irrelevant if the bus is in the wrong state, required equipment is unavailable, or the mechanic lacks the necessary authorization. Correlated observations also need care. Two measurements of essentially the same condition should not create false certainty merely because the system counts them as independent evidence. The tool needs a way to stop when the remaining tests are unhelpful and hand the full case to an engineer. A recommendation to escalate can be the correct result, especially when the observed symptoms fall outside the prototype's approved scope.

An Engineering owner should review the test catalogue and version changes, while workshop staff should help design the recording interaction so it does not add more work than it removes. Integration with the work-order system should preserve the original report, every entered observation, the recommendation shown, and the final confirmed finding. If the tool or its data connection fails, the mechanic returns to the approved existing diagnostic process. The system should retain partial observations for later reconciliation without suggesting that an unfinished session reached a diagnosis. Ongoing maintenance involves reviewing unseen causes and updating the catalogue when equipment or procedures change.

The pilot comparison should use the same blinded staged cases for the proposed sequence and the current checklist. Count tests and time before an independently confirmed cause, but also count incorrect conclusions, unnecessary replacements, and appropriate escalations. Fewer tests are not a benefit if the tool reaches the wrong conclusion more often. LionLink should fund the catalogue and staged comparison only if engineers identify a genuine branching diagnostic problem that a simple checklist does not already handle. If the adaptive order remains useful across plausible assumptions and technicians can explain its recommendations, a supervised workshop trial is justified. Otherwise, the catalogue itself can improve the existing procedure without committing to a probabilistic diagnostic product.
