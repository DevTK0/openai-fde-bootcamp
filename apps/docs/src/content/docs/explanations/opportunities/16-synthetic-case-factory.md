---
title: Testing unusual passenger reports without copying passenger stories
description: A reproducible generator can create deliberately varied fictional cases with known expected results for software tests.
---

A developer changes the form that matches a passenger report to a journey. The familiar examples still work, but a report spanning midnight is now interpreted against the wrong service day. Another report names a scheduled departure while the matching logic treats the time as an observed departure. These illustrative failures can remain hidden when a test collection contains only a few ordinary cases. Adding more records does not necessarily help if every new record exercises the same assumptions.

The proposal is to generate fictional passenger cases from explicit rules, with an expected interpretation attached to each case. The generator would help developers test unusual combinations repeatedly without copying real passenger narratives into development environments. LionLink's current dataset is already fictional, so this is not a response to a demonstrated privacy breach. Its immediate value would be systematic test coverage. Its future data-minimization value would be avoiding dependence on private stories if the application later handles real operational records.

The existing passenger schema provides a useful starting point. Reports include a journey window, a time basis, a reported service and stop, and narrative text. The [passenger findings](/docs/passenger-findings/) explain why a scheduled journey and an observed departure need different matching rules. The [evidence sources](/docs/applications/) identify the accounts as a selected fictional collection. Those examples show categories worth reasoning about, but they do not constitute a complete specification of correct matching. A product owner must first decide what the application should do with ambiguous, incomplete, and contradictory reports.

The generator would choose a case category, create compatible structured fields, and render an independently written narrative from those fields. A seed is a saved starting value for the generator's random choices. Giving it the same seed and rule version produces the same cases, so an engineer can reproduce a failure reported by another developer. Each output would record its category, seed, and expected result. The generator is therefore producing test inputs together with an explanation of what they are meant to test, rather than a collection of realistic-looking stories whose meaning nobody has checked.

For an illustrative midnight case, the rules could create a journey window that begins before midnight and ends after it, with the dates stated explicitly. A narrative template would describe that same interval. The expected result might be that the report is valid but cannot be assigned to a single journey without another identifier. A separate invalid category could reverse the start and end times while keeping the same date. Its expected result would be a clear validation error. The distinction is useful because an unknown match is not the same as an invalid report. The application should not reject a valid passenger account merely because the available evidence cannot identify the trip.

Other categories can remove a vehicle identifier, provide an unknown stop, or introduce a deliberate conflict between the selected service and narrative. Each invalid case should normally break one chosen rule, allowing a failed test to identify the relevant behaviour. Valid cases must remain consistent across structured fields and text. If a generator accidentally introduces several unrelated contradictions, its tests become difficult to interpret. The quality of the rule catalogue and expected results matters more than the number of records generated.

The mechanism deliberately avoids learning from or paraphrasing passenger narratives. A model that rewrites private stories can retain identifying details or unusual combinations, and random names do not solve that problem. Here, authors write templates independently and use invented identifiers within a controlled fixture network. The generator reads only approved rules and fictional reference data. Engineers can enforce that boundary through an explicit input allowlist and a test that fails if the generator attempts to read a passenger-narrative source. This is a narrow, inspectable design choice, not a claim that synthetic data automatically guarantees anonymity.

For a small application, a handful of hand-written tests may be clearer and cheaper. The generator becomes worthwhile when several consumers need the same categories, when date and identifier combinations produce many meaningful variants, or when failures need exact reproduction across environments. It should supplement a small set of reviewed examples rather than replace them. A generator and the application can share the same mistaken assumption. Independent examples with literal expected results provide a check against that risk, particularly for the most consequential matching rules.

A bounded implementation would cover scheduled versus observed time, midnight boundaries, missing identifiers, and conflicting service references. The output would be a fixture pack used by the journey-matching form and its import validation tests. Passenger-service staff would review whether the fictional wording expresses the intended ambiguity. Developers would define how the pack enters existing tests and how seeds appear in failure messages. The product owner would approve the expected behaviour. No connection to a live passenger system is required, and there is no reason for the generator to receive access to production narratives.

Ongoing work would consist of updating the rules when matching behaviour changes and adding a category when an actual defect reveals a missing case. A new category should describe the general failure without copying the passenger's story that exposed it. Rule versions must remain attached to generated packs so that a changed generator does not make an old failure impossible to reproduce. The system should stop if it cannot produce a valid case under its own constraints, rather than emit a contradictory record to meet a requested count. Developers also need a way to inspect a small sample without reading thousands of outputs.

The pilot should test whether the fixture pack catches plausible mistakes in a real consumer. Engineers can deliberately alter date handling or remove the distinction between scheduled and observed time, then confirm that the relevant test fails for the expected reason. They should also verify that repeated generation with the same seed is identical and that every category has a reviewed expected result. Useful measures include meaningful defects detected, time to reproduce a failure, and maintenance effort per category. Record volume is not a success measure, and these fixtures cannot establish performance on the real passenger population.

LionLink should start by writing the case catalogue and the independent expected outcomes. If that exercise reveals only a few stable cases, ordinary fixtures are sufficient. If the application needs many controlled variations and several teams would reuse them, a small generator is justified. The deliverable to fund is a reproducible test asset with a clear privacy boundary and useful behavioural coverage. A broad synthetic-data platform would be unnecessary until those concrete consumers demonstrate a need.
