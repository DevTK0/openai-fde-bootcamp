---
title: Checking whether a relief driver can complete the whole assignment
description: How explicit duty rules could expose missing breaks, qualifications, travel, and return time before a controller approves cover.
---

A controller has found a spare bus and a driver who appears to be free. The outward journey fits the available time, so assigning the driver seems reasonable. The return movement may finish after the driver's availability ends, however, or the handover may consume part of a protected break. Discovering that conflict after departure leaves operations with a problem that could have been identified before approval. This proposal would check a complete proposed duty against agreed rules and explain exactly which part passes, fails, or cannot be assessed from the available information.

The LionLink exercise has a useful starting point. Its crew records describe service qualifications, availability windows, protected breaks, maximum continuous duty, and takeover time. Incident planning also includes crew commitments and rest. As the [evidence sources](/docs/applications/) make clear, these are fictional exercise records with limited coverage. They are not employment rules for a real operator, and a pass against them would not establish legal compliance. Their value is that they expose the shape of the operational question: the same person must remain qualified, available, and able to move between every part of an assignment.

A roster supervisor can check those requirements manually. For a small number of familiar duties, that may remain the best method. The implementation case arises when disruption causes frequent changes, several systems hold different parts of the duty, or reviewers repeatedly miss the same boundary conditions. A checklist reminds someone to ask about the return journey. An executable checker can calculate whether that return actually fits every time the proposed journey changes. The investment should depend on evidence that repeated calculation and incomplete information cause mistakes, not on a general claim that people are bad at planning.

The proposed system begins with a timeline rather than a label such as available driver. The timeline records driving, travel to the takeover point, the takeover itself, waiting, other committed work, rest, and the return movement. Each entry has a beginning, an end, a location, and a defined kind of activity. Approved rules inspect that timeline. One rule checks whether the driver is qualified for the service. Another checks overlaps with protected rest. A different rule accumulates the activity that the organization defines as continuous duty. Keeping those definitions explicit prevents different reviewers from unknowingly applying different meanings of work or break.

Consider an illustrative relief duty with a protected break beginning at 11:00. A proposed drive finishes at 10:55, which appears acceptable when viewed alone. If an approved ten-minute handover follows that drive, the complete assignment reaches 11:05 and overlaps the break. These times are explanatory assumptions, not a supplied LionLink duty. The checker would point to the handover interval and the break rule, rather than display a vague failure against the whole shift. The controller could then propose a different takeover, another driver, or a revised timing and run the checks again.

A missing earlier part of the day requires a different answer. The driver might satisfy the current availability window while already having accumulated work relevant to a continuous-duty limit. If the checker has no preceding history, it should return unknown for that rule rather than treating missing activity as rest. The result should explain which information is missing and which conclusions remain possible. This distinction is central to the proposal. An apparently reassuring green result based on a partial duty would be more dangerous than a manual process that openly acknowledges uncertainty.

The first deliverable should evaluate one supplied duty and a proposed relief assignment, with a readable explanation that a roster supervisor can review. The team should create deliberate variations: a valid complete assignment, a slight break overlap, an unqualified service, a late return, and missing prior activity. Reviewers should agree the expected outcomes before the implementation runs. The prototype does not need to find the best replacement driver or rebuild the whole roster. It checks an arrangement provided by a person or another planning tool, which keeps the responsibility and the evaluation manageable.

The most substantial work will be agreeing the rules and their sources. A roster specialist must identify the authoritative qualification register and the approved interpretation of each duty rule. Operations must supply credible positioning and takeover durations. Anyone responsible for employment agreements or applicable obligations must review the production rules through the organization's normal process. Where two specialists disagree, the software team should record the unresolved interpretation rather than choose the easiest condition to code. A checker can apply an agreed meaning consistently, but it cannot create agreement merely by converting one interpretation into software.

Every result should retain the input timeline and the rule version used. Otherwise, a later change to a break definition could make an old accepted assignment appear to have passed under rules that did not exist at the time. Cross-midnight work and local-time handling need explicit examples because a duty can extend across dates without becoming two independent assignments. Integrations should initially read roster information and return advisory results. Approval remains with the authorized supervisor, who can distinguish a missing fact from a genuine exception and record the disposition rather than bypass a warning without explanation.

For adoption, the explanation needs to appear where a controller proposes cover. A separate tool that requires staff to retype the whole duty risks creating new omissions. If an input changes after checking, the previous result should visibly become outdated and require another check before it supports approval. During an integration outage, the interface should show which information is unavailable and direct the user to the existing manual review process. The checker should not block every operation merely because it cannot assess an optional advisory rule, but the operator must define which unknown mandatory checks prevent approval.

The pilot should compare independent manual judgements with the checker on realistic complete and incomplete cases. The team should measure missed conflicts, false failures, time needed to understand explanations, and how often missing data prevents a useful result. If reviewers cannot agree expected results, the immediate need is policy clarification rather than more implementation. If reliable inputs exist and the checker consistently catches meaningful conflicts without obscuring judgement, LionLink can integrate it into relief assignment approval. The next funded step should therefore be a small set of jointly approved duty examples and rule definitions, followed by a checker that proves those definitions are usable in practice.
