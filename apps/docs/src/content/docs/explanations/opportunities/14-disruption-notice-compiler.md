---
title: Giving passengers consistent instructions during a disruption
description: Approved incident facts can produce matching language and channel versions without separate edits changing their meaning.
---

During a stop closure, passengers need a usable instruction. They need to know which stop is unavailable, when the change applies, and where to board instead. In an illustrative LionLink incident, a communications officer updates one message with a replacement stop while another language version still names the old location. Each message reads fluently, yet the versions direct passengers to different places. The problem is the loss of shared facts as staff copy and edit messages under time pressure.

The proposed service gives the communications officer one approved incident record and generates the supported notices from that record. It would not decide what happened or invent a recovery time. An authorized editor would confirm the operational facts, choose the applicable incident type, and review the resulting messages before publication. The value would be fewer opportunities for locations, times, and required actions to diverge between versions, together with a clear record of which channels still need an update.

LionLink's fictional operating records contain timestamped resource updates, associated stops and trips, and control instructions that reference earlier updates. They show possible evidence that an editor could consult. They are not ready-made passenger notices, and they do not establish that LionLink currently publishes contradictory translations. The [evidence sources](/docs/applications/) describe the extract's boundaries. The [reliability findings](/docs/reliability-findings/) also distinguish observed delay from an explanation of its cause. A publication system must preserve that distinction instead of turning every internal statement into a public assertion.

The mechanism uses structured incident records and reviewed message templates. A structured record separates the affected stop, start time, alternative boarding point, and status time into distinct fields. Each incident type has its own required information. For example, a stop closure needs a replacement instruction, whereas a delay notice may need a service identifier and a current status without a promised end time. A compiler is the part of the system that checks those fields and turns the approved record into complete messages. Here the term means applying explicit rules, rather than asking a language model to improvise the notice.

For an illustrative closure, an editor selects the affected stop from LionLink's stop directory and enters a confirmed alternative. The compiler inserts the approved passenger-facing names into the reviewed templates for each supported language. It formats the same effective time in each version and produces a preview for the chosen channel. If the editor leaves the alternative blank, the closure notice cannot proceed because the required passenger action is missing. If a channel's character limit would remove that action, the system blocks that output and requests a suitable reviewed short template. It must not silently truncate the instruction.

Suppose operations later changes the alternative boarding point. That change creates a new incident revision, and the previous previews no longer qualify for publication as the current notice. The officer reviews the replacement versions and can see which channels have accepted the update. A channel that fails to update remains visibly outstanding. The system cannot undo a message already read, but it can preserve the publication history and support a correction. This version control is essential because even a perfectly translated old instruction becomes misleading after the underlying facts change.

A shared document with approved examples may be sufficient if LionLink issues few notices in a single channel. Training staff to update a common source can solve part of the problem without custom software. The stronger case for this proposal arises when the same incident repeatedly needs several language and channel versions, and manual checks struggle to keep them aligned. A free-text drafting assistant addresses wording speed but cannot by itself guarantee that every version contains the same required location and time. The proposed rules deliberately trade some flexibility for control over the facts passengers act on.

The first deliverable should support two common incident types, two languages reviewed by fluent specialists, and one text channel. Communications staff would supply the approved wording and define the information each type requires. Operations would identify who can confirm the incident facts. Engineers would build the editor, required-field checks, previews, revision approval, and publication receipt. Stop identifiers would link the editor to the network directory, but passenger-facing stop names would need review. An internal location label that is convenient for controllers may be confusing on a roadside notice.

The initial scope should also include a separate exceptional-incident path. Some disruptions will not fit the supported templates, and forcing them into the nearest type can produce a misleading message. An editor should be able to use the established reviewed free-text workflow without claiming that the compiler validated it. Template coverage can expand after staff record the exceptions they actually encounter. The owner of the template library needs a process for reviewing language changes, retiring outdated phrasing, and testing existing notices after a revision. That editorial work is a recurring operating cost.

Failure recovery depends on preserving human publishing capability. If a channel integration is unavailable, the officer should be able to copy the approved output and record manual publication. If the system itself fails, staff need access to the approved templates and current incident facts through the existing fallback process. Permissions should distinguish editing facts, approving a revision, and publishing it. A correction must retain who changed the instruction and why. These controls support accountability, but they do not prove that an operational source was accurate. The editor still owns the decision to treat information as confirmed.

A useful evaluation begins with historical-style scenarios and deliberately incomplete records. Reviewers should inspect whether each output contains the same location, time, and action. They should test changes after approval and confirm that stale previews cannot publish. Fluent reviewers must assess meaning and readability because a software check cannot establish translation quality. In an operational pilot, compare preparation time, correction work, inconsistent versions, and the delay between a changed fact and updates to every supported channel. Faster publication is not a benefit if it increases factual errors.

LionLink should first ask communications staff to identify recurring notice types and demonstrate where the current process loses consistency. If they can express those incidents with a manageable set of facts and reviewed templates, a narrow implementation has a clear rationale. If incidents are overwhelmingly exceptional or approved translations cannot be maintained, a better shared drafting and review process may be more useful. The investment decision should fund ongoing editorial ownership along with the software, because a compiler can enforce reviewed language only while that language remains correct.
