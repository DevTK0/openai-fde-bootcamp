---
title: Testing whether festival shuttles can clear the crowd before closing
description: Why LionLink should compare complete event transport plans under different arrival and delay scenarios before committing vehicles and crews.
---

An event planner can assign enough bus seats to match an expected crowd and still leave people waiting at closing. Seats are available only when a bus reaches the boarding point, and a bus carrying passengers cannot immediately load its next group. If crowds arrive in a burst or a return journey takes longer than planned, total capacity hides the problem. This proposal would let LionLink compare festival shuttle arrangements by following passengers, buses, and crews through the event, so the planner can see when each arrangement becomes unable to clear the queue.

The fictional festival planning records identify two temporary routes, route cycle times, proposed departures, planning capacities, wheelchair spaces, crews, and event requirements. The [evidence sources](/docs/applications/) distinguish such planning inputs from observed operations. The records are enough to construct an initial model of the proposed service. They do not tell us the real pattern of crowd arrivals, actual travel-time variability, or how many passengers need an accessible space. Any recommendation must therefore state which demand and delay assumptions it depends on. An impressive-looking simulation cannot turn those assumptions into measurements.

The current workaround for this kind of decision may be a spreadsheet that divides expected passengers by seats per departure. That is a useful first check and may suffice for a small event with predictable arrivals and generous spare capacity. The harder question concerns timing. If a later departure has empty seats but passengers arrived after the final boarding cutoff, the earlier capacity cannot help them. Similarly, a nominal spare vehicle adds no usable service if its crew cannot complete the return. The proposed model is worthwhile only when those interactions can change which resource plan the operator chooses.

The method is discrete-event simulation. Instead of drawing a continuous animation, the calculation advances whenever something relevant happens: passengers arrive, a bus becomes available, boarding finishes, or a vehicle returns. At each departure, the model boards eligible passengers up to the assigned capacity and leaves everyone else waiting. It tracks wheelchair spaces separately because an empty general seat does not necessarily meet an accessibility need. The same declared events and delay assumptions run against each proposed service plan. That makes the comparison about the plan rather than about giving one alternative an easier crowd.

Imagine an illustrative crowd of eighty people arriving shortly before the first shuttle, with two departures that can each take fifty people. A total of one hundred spaces sounds sufficient. If thirty more people arrive after the first bus leaves, the second departure cannot clear everyone, even if its full capacity is available. These numbers are invented to explain timing, not to describe the LionLink fixture. The model would show the remaining queue after each departure and the time those passengers have already waited. The planner could then test an additional departure, a permitted reassignment, or an earlier operating change using exactly the same arrivals.

That example becomes more useful when the model includes the vehicle's return and the crew's full commitment. Adding a departure might make the queue smaller but require a bus that has not returned. Reassigning a bus from the other shuttle might transfer the unresolved queue elsewhere. A late return might push a driver's duty past its allowed window. The model should flag these cases as invalid plans, not report their attractive passenger results as if the resources existed. Engineering release and conditional availability also remain explicit prerequisites. The planner must confirm them outside the simulation before accepting a resource commitment.

The first deliverable should reproduce the two supplied temporary routes with a small set of agreed scenarios. It should start with deterministic arrivals and journey times so planners can check several departures by hand. Only after those results match should the team add variable demand or travel times. The useful output is a comparison of waiting time, the queue at closing, accessible-demand outcomes, and any resource violations. A clear record of the assumptions matters more than animation. The tool should retain a reproducible scenario so a controller can ask why a plan failed and inspect the relevant sequence.

The event organizer and operations planner must jointly own the demand assumptions. Ticketing counts, entry and exit observations, event timings, or counts from comparable events may help, but none is present in the supplied extract. The team also needs boarding-time assumptions, route travel observations, stopping arrangements, and an explicit treatment of passengers who leave the queue. An accessible-service representative should review how passengers with different boarding needs enter the model. If those inputs are unavailable, the tool can still identify conditional limits, such as the largest arrival burst a plan can clear under a stated travel time, without claiming that burst is likely.

Uncertainty needs careful interpretation. Running a model thousands of times with one guessed arrival pattern does not remove uncertainty about that pattern. The planner should compare several plausible demand shapes and delayed-return cases before relying on an average result. If one plan performs well for gradual arrivals but badly after a concentrated event finish, the recommendation must explain that dependence. Where the preferred plan changes under assumptions the team cannot resolve, the model should support a contingency decision or a request for better observations. It should not hide the disagreement behind one combined score.

Verification begins with passenger accounting. Everyone who arrives must either board, remain waiting, or leave through an explicitly modeled behavior. The model also needs to preserve vehicle identity and crew availability through complete returns. Operational evaluation comes next. Planners should compare decisions made with their existing spreadsheet against decisions made with the simulation, then inspect whether the additional detail changes a resource choice or contingency trigger. A later event pilot could compare predicted queue development with observed counts. Persistent mismatches would require revision before the tool informs another commitment. No saving or reliability improvement can be claimed from the exercise alone.

LionLink should invest in this model if event planners face consequential choices between complete shuttle arrangements and can supply defensible ranges for crowd and travel behavior. If every plausible case already has ample spare capacity, a spreadsheet and a clear event plan may be enough. The next decision is to agree a limited set of crowd and return-delay scenarios with the event team and test the supplied allocations against them. The implementation earns further support when it exposes a resource or timing weakness that changes the plan, or shows which measured input would resolve an otherwise uncertain decision.
