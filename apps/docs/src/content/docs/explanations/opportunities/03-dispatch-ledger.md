---
title: Preventing conflicting dispatch instructions for the same bus or driver
description: Why LionLink may need one authoritative record of accepted assignments, acknowledgements, and cancellations.
---

Two LionLink controllers are trying to recover disrupted services. Each sees a spare bus as available and assigns it to a different trip. Both decisions may have looked reasonable when made, but only one can be carried out. A late message adds another difficulty if a driver receives an older instruction after a replacement instruction. The problem is no longer which assignment would be best. It is establishing which instruction has authority, which resources that instruction commits, and whether the people expected to act have received it.

The fictional operating extract includes control actions linked to trip, vehicle, crew, and resource updates. The [evidence sources](/docs/applications/) explain the selected operating coverage and its limits. These records can support a demonstration of assignment history. They do not show that LionLink currently suffers duplicate dispatches, nor do they establish that an authoritative transaction service already exists. Before implementing another system, the team should inspect the existing dispatch product and operating procedure. If one dispatcher already owns every assignment through a reliable system, adding a separate record could create the very ambiguity this proposal intends to remove.

Where multiple people or integrations can issue assignments, the proposed solution is a command ledger. This is a permanent sequence of decisions about instructions, with the information needed to explain each acceptance or rejection. A new assignment arrives as a request rather than becoming authoritative merely because someone pressed a button. The service checks that the trip, bus, and driver are still in the state the controller reviewed. It reserves the necessary resources and records the accepted instruction in one transaction. A transaction makes those changes succeed together or not happen at all, preventing an instruction from being recorded without its resource reservation.

Suppose, as an illustrative case, both controllers prepare assignments while bus A is free. The first request reaches the service and reserves bus A for a trip. The second request includes the older version of the bus's availability. The service rejects that request and tells the second controller which accepted assignment now conflicts. The controller can review another bus or revise the recovery plan. A warning shown only when the page first opens would not provide the same protection because the competing request might arrive after that warning. The check must happen at the moment the system accepts the assignment.

Connectivity failures require a related rule. If a controller submits an assignment and loses the response, pressing submit again should retrieve the same decision rather than reserve resources twice. Each intended command therefore needs a stable identifier that remains the same during retries. The ledger retains the outcome associated with that identifier. This property is called idempotency, but the user's experience is straightforward. Repeating an uncertain submission cannot create a second instruction. A genuinely revised instruction gets a new identifier and an explicit relationship to the instruction it changes.

Acceptance and delivery are separate facts. An accepted assignment means the system has committed the resources. It does not mean the driver has read or acknowledged the message. The user interface should distinguish a proposal, an accepted command awaiting delivery, a delivered command, and any required acknowledgement. A cancellation also needs its own recorded instruction. Deleting the original entry would erase what the driver might already have acted on. If a cancellation cannot reach the driver, a controller needs to resolve that situation through the established operating procedure rather than assume the resource is free again.

The first implementation should be a small service exercised by simulated controllers against the supplied action and resource sequence. Two clients should compete for the same bus, one should repeat a request after a simulated timeout, and an old update should arrive after a newer accepted decision. After a restart, rebuilding the current assignment view from the recorded events should recover the same commitments. This replay ability helps investigate a disputed instruction because the system can show what information supported the decision at the time. It is a consistency tool, not a search assistant that summarizes a transcript and guesses which message prevailed.

The difficult prerequisite is organizational authority. Operations must define which system owns an assignment and how emergency radio instructions enter that record. A disconnected depot might need an explicit local operating procedure, but the software cannot promise globally exclusive resources while independent disconnected systems all remain free to allocate them. The first release should therefore show an unresolved request as pending when it cannot reach the authority. Any necessary manual instruction should enter a reconciliation queue after service returns, with a controller deciding how to resolve conflicts. A sponsor should not approve deployment until that procedure is usable during an actual communications failure.

Integration also needs stable identifiers for trips, crews, and vehicles, reliable update ordering, and access controls tied to operational roles. Occurrence time and arrival time must remain separate because a late resource update does not automatically describe the latest state. Engineering release and crew eligibility checks belong before acceptance where the relevant information is authoritative. The ledger cannot make a bad operational decision safe merely by preserving it. Existing systems should read the accepted assignment state through a defined interface rather than maintain a second independently editable copy. Maintaining that ownership boundary is a larger commitment than building the initial database.

A pilot should first prove the failure behavior. Competing commands must produce only one accepted reservation, retries must return the original outcome, and a restart must preserve the assignment state. Controllers should then rehearse delayed delivery, cancellation, and manual recovery cases. The business comparison is with current reconciliation work: how often staff must clarify conflicting instructions, how long they spend reconstructing decisions, and whether the new process adds unacceptable delay to urgent dispatch. The fictional fixture supplies no baseline rate or financial saving. Those observations need collection from the real workflow before a return on investment can be argued.

This project earns implementation when LionLink has several legitimate assignment writers and evidence that coordination failures are costly or hard to investigate. It is less attractive when the issue is an unclear handover between two people that a single-authority procedure would resolve. The next decision should be an authority and failure-recovery design review with controllers and the owners of current dispatch integrations. If they can agree one accepted-command record and a workable offline procedure, the prototype can test whether transactional acceptance makes that agreement reliable under contention and failure.
