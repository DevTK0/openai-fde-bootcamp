---
title: Checking that an Engineering release record is genuine
description: Digital signatures can verify who issued a release statement and whether it changed, while preserving the limits of offline checks.
---

A controller receives a release record for a vehicle while the workshop system is unreachable. The message may be genuine, but a screenshot does not provide a dependable way to establish who issued it or whether someone changed the vehicle identifier. Calling Engineering may be the correct existing response. If that verification problem recurs across teams or disconnected locations, LionLink could use a signed release certificate to check the authenticity of the statement without needing to contact the issuing system for every read.

The proposed certificate has a narrow purpose. It establishes that an authorized signing service issued particular release facts and that those facts have not changed. It does not establish that the vehicle remains roadworthy, that no new defect has appeared, or that a controller may dispatch it. Those decisions still depend on current operational checks and authority. The distinction matters because a mathematically valid signature can be attached to a statement that was true when issued but is no longer sufficient for today's decision.

The fictional workshop records include a work-order reference, vehicle identifier, confirmed release time, and release status. Readiness records also describe availability intervals and release state. The [workshop findings](/docs/workshop-findings/) explain why tentative completion cannot substitute for confirmed Engineering release. As described in the [evidence sources](/docs/applications/), these are supplied exercise records. They are unsigned and do not demonstrate current forgery, an established trust relationship, or a need for offline verification. The first investigation should establish how staff currently authenticate release information and where that process fails or delays work.

A digital signature uses a pair of cryptographic keys. The issuing service keeps one key secret and uses it to sign the exact certificate contents. Verification devices receive the corresponding public key, which lets them check the signature without gaining the ability to issue certificates themselves. If someone changes a signed vehicle identifier or release time, the check fails. The public key must arrive through a trusted administrative process. Accepting a key supplied by the same unknown sender as the certificate would prove little, because that sender could have created both.

In an illustrative workflow, Engineering confirms a release in its existing system. An authorized signing service then creates a certificate containing the issuer, certificate identifier, vehicle, work order, release scope, issue time, and expiry. The controller receives it as a file or scannable code. The verification device checks the signature against a trusted key and compares the vehicle and work order with the intended use. A genuine certificate for a different vehicle must fail that use check even though its signature is valid. The result should separate authenticity from whether the certificate currently meets LionLink's acceptance policy.

Suppose Engineering later withdraws the release because a new issue appears. The certificate's original signature remains valid, so LionLink also needs revocation information, a record that particular certificates or issuing keys should no longer be accepted. An online verifier can consult the current revocation source. A disconnected verifier can consult only the copy it last received. If that copy is older than the policy permits, the device must report that it cannot confirm current acceptance. No cryptographic method can reveal a new withdrawal to a device that has received no new information.

This limitation determines whether the project is useful. If operations requires immediate knowledge of every revocation, offline acceptance cannot meet the requirement. Staff must contact the authoritative system or use the established escalation process. If a bounded age of revocation information is acceptable for the narrow authenticity check, Engineering must explicitly approve that policy. Short certificate validity can reduce how long an old statement remains usable, but it also increases dependence on issuing fresh certificates. Reliable device time is another requirement because expiry checks are meaningless when the verifier cannot trust its clock.

A read-only view of the authoritative workshop system may be simpler and stronger wherever connectivity is dependable. A signed certificate becomes more useful when the statement has to cross organizational boundaries or remain independently verifiable during a defined interruption. It adds key management and revocation operations that a normal record lookup does not need. That extra complexity should solve a demonstrated authenticity problem. It should not be adopted merely to make existing releases appear more secure, and it must not weaken the current release or dispatch approval process.

The first deliverable should use disposable test keys and fictional release records. It would include an issuing service, a certificate format with unambiguous field encoding, a verifier, and a small revocation feed. Unambiguous encoding means that the issuer and verifier agree exactly which bytes represent each field, so differing interpretations cannot produce a misleading result. Engineers should use established cryptographic libraries rather than invent a signing algorithm. Engineering would define the release scope and validity policy, while the security owner would define key custody, trusted-key distribution, replacement, and compromise response.

The production integration would issue a certificate only after the authoritative release transition succeeds. It must not sign an expected completion as though it were a confirmed release. Devices need a supported method to update trusted keys and revocation information, and the verifier should show the age of that information. If a key is suspected of compromise, staff need a tested procedure to withdraw trust, issue a replacement, and handle certificates created under the old key. The operational burden includes monitoring those updates and rehearsing recovery, not merely renewing an occasional file.

A useful prototype should demonstrate the original certificate passing, a modified field failing, a wrong-vehicle use failing, and an expired certificate failing. It should revoke a certificate and show that a refreshed device rejects it. An older disconnected device should state its freshness limit rather than pretend to know about the withdrawal. Tests should also cover missing trusted keys, an unreliable clock, and a lost connection during a revocation update. Independent verification of the certificate format helps show that acceptance does not depend on one interface hiding an incorrect interpretation.

The pilot's business measures should concern the actual verification workflow. Compare time spent contacting Engineering, unresolved authenticity checks, administrative effort, and cases where stale information prevents acceptance. The value is a dependable answer to who issued which statement, not permission to skip current readiness checks. LionLink should first agree whether a bounded offline authenticity check meets an operational need. If it does, a narrowly scoped pilot with key-management ownership is defensible. If immediate revocation knowledge is essential or the current online lookup is adequate, the better decision is to improve that authoritative access rather than introduce signed certificates.
