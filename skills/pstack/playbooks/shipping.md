### Shipping

**You own what lands. Verify each PR independently, land only the verified run from the root, then keep your hands off the queue.**

This is the half after `babysit.md`.

1. **Resolve the forge, then verify every PR independently.** Use Codex's authenticated PR tools or the repository's forge CLI consistently, and follow the PR registration instructions in [Opening a PR](opening-a-pr.md). One independent verifier per PR, run sequentially, using available Codex subagents and the repository's verification skill or runtime tools against parent versus head. If no independent verifier is available, stop before merging and report the missing gate; self-review is not a passing verdict. Each returns `PASS`, `PASS+NOTES` or `FAIL` and records the verdict with evidence. Post it on the PR only when comments are authorized. Safe means a verdict from an agent that did not write the code. CI green is not a verdict, and an approving bot review is not a verdict.
2. **Land only the contiguous verified run rooted at the bottom.** Walk up from the lowest unmerged PR and stop at the first one without a passing verdict, where both `PASS` and `PASS+NOTES` pass. A verified PR sitting above an unverified one is not landable. Report the ceiling as a PR number and say what breaks the chain.
3. **Re-check that each verdict describes the exact revision.** Record the verdict head SHA and base SHA. Before landing, fetch and compare both with the current PR head and target base tip. Any changed head or base invalidates the verdict, including rebases, base retargets, whitespace-only edits, and changes confined to tests, docs, or configuration. Run independent verification again against the new pair and require CI on the current head. `git patch-id` ignores whitespace and cannot prove semantic equivalence; never use it, matching commit messages, or similar build output to carry a verdict across revisions. Even when both SHAs match, refresh mergeability, required checks, review requirements, and queue state immediately before landing.
4. **Prepare only the bottom PR.** Fetch current trunk. Rebase the lowest verified branch onto the exact trunk tip when needed, push it, and retarget only that PR to trunk through the selected forge. Re-run step 3 after the push. Do not retarget, arm, or merge descendants yet.
5. **Land one PR at a time.** If the bottom PR is mergeable now, merge it through the selected forge using the repository's allowed merge method, preferring squash. If requirements are still running and the user asked for merge-when-ready, arm only that PR, and only when a required forge gate binds independent verification to the final merge-group head and base and invalidates it whenever either changes. Confirm that enforcement before enabling auto-merge or queue admission. This port does not install such a gate. Without it, keep the PR unarmed, wait for readiness, repeat step 3, and land directly only while the verified revisions remain current. If a mandatory queue cannot enforce this gate, report the missing capability and stop before enqueueing. Never bypass branch protections. Wait for that PR to merge before preparing the next one.
6. **Do not read GitHub `autoMergeRequest` as stack readiness.** At most it says GitHub auto-merge was requested for one GitHub PR. It does not prove that a descendant is queued, that a patch verdict is current, or that the contiguous stack is safe. Confirm the active forge's state for the current bottom PR, and say that the state is unknown if the active forge cannot report it.
7. **Recompute after every merge.** Fetch trunk, confirm the merged SHA is present, drop the merged PR from the frozen bottom-to-top list, and inspect the new bottom PR's base, head, checks, and verdict head/base SHAs. The forge may retarget a child automatically, but do not assume it did. Repeat steps 3 through 6 for that one PR. Independent work stays outside this chain and ships on its own.
8. **Watch the current frontier until it merges or fails. Do not mutate the queue around it.** Use bounded forge status polls or an available PR watcher, then re-read the PR's head/base revisions, merged state, checks, review decision, mergeability, and queue state. A revision change returns an unarmed PR to step 3; an armed queue entry must remain blocked by the required revision-bound gate until fresh independent verification passes. Polling alone cannot protect against a base change between polls. Checks completing is not proof of a merge. Only run step 7 after the forge confirms it merged. A closed-unmerged PR or a definitive blocking failure stops landing. Pending checks or queue admission are pending, not success or failure. Respect stop requests and session limits; report outstanding auto-merge state if the session ends. Report each merge and the new ceiling. If the queue stalls, diagnose before mutating.
9. **Stop at the ceiling.** When the verified run is merged, report what landed, what the next unverified PR is, and what verifying it would take. Extending the run is a new pass through step 1.

**Reply:** the verified run and its ceiling, each PR's verdict and who produced it, what you armed and how you confirmed it, what landed, and what the next gap needs.
