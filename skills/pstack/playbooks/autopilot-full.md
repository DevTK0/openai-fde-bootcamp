### Autopilot-full

**You own the verdicts, never the PRs. One owner runs each PR from build to merge, and nothing merges without your clean swarm verdict.** For "autopilot this queue", "full autopilot", and one-owner-per-PR programs. Each PR's owner carries the whole lifecycle through merge; the coordinator owns independent verification, countersigns, and audits.

Before execution, record the queue, acceptance criteria, trunk, operator-owned items, and merge grant. A request to install or explain these playbooks is not a request to execute a queue. A request to execute Autopilot-full grants landing authority within its stated scope unless the operator withholds it. Without that grant, deliver merge-ready work or use Autopilot-stack. Both modes run only while the supervising Codex session remains active; no scheduler or external worker service is installed.

Confirm that each change has a runnable verification recipe and isolated environment. Use an existing app-specific verification skill or a concrete driver with observable acceptance criteria. If neither exists, use **create-verification-skill** within scope before starting owners, or report the missing prerequisite. Never substitute green CI for live behavioral proof.

1. **Mark the operator's items and honor state-then-wait.** Items the operator names stay with the operator. The operator reviews and clicks, and no owner merges one. When the operator asks for the protocol or the plan to be stated, deliver the statement and stop. Execution starts only on the operator's explicit go.
2. **Spawn one owner per PR with the full lifecycle and an early trail.** Resolve the forge once for the program. Use the available Codex PR tools or authenticated repository forge CLI. Resolve the remote and trunk branch rather than assuming `main`. Follow PR registration and body-file rules in [Opening a PR](opening-a-pr.md) for every owner and every stack layer. One Codex owner agent per PR owns build, the first push, an early PR, self-proof on the real artifact (the **prove-it-works** principle skill), reviewer feedback triage per `../references/reviewer-feedback.md`, direct diff cleanup, comment review, a rebase onto current trunk, the babysit loop to green (`babysit.md`), and the merge itself. Within about 15 minutes, every owner starts a `decisions.tsv` trail per the **show-me-your-work** skill, pushes its first branch snapshot, and opens an early PR with its current verification status clearly stated, respecting an explicit draft preference. After that, the owner pushes its branch again after every verifiable unit (hooks on, a WIP commit is fine). Open the PR before self-proof so the URL, decisions, and checks form a durable trail. Keep `decisions.tsv` uncommitted and return it with the reports. As soon as a subagent starts, the owner adds its ID, expected runtime (at least the longest past run of that kind), and state to a `children.tsv` kept the same way. The owner does the first rebase before the code-ready report and babysit, whether or not trunk has drifted. In fix rounds, the owner keeps that merge base. The owner rebases again only at merge prep (step 5), on a `git merge-tree` conflict with trunk, or on a CI failure that comes from a change on trunk. When the shipped code is final, after direct diff cleanup and comment review, it reports the code-ready head SHA. It also reports the SHA of each later push that changes the patch. Self-proof, CI, and babysit may run alongside the swarm only with isolated writable/runtime state and available slots. Reserve slots for verifier lanes; otherwise run these stages in waves. The owner reports merge-ready with the head SHA when self-proof, CI, and babysit finish. Before a push that starts a round, run the pre-review checks that the repo's AGENTS.md files and rules name for the touched paths. Run them on the committed head. A hook pass is not proof. To publish each rebase, capture the expected remote tip with `ls-remote` and use an explicit `--force-with-lease=<ref>:<expected-sha>` on the owner's branch. Stop if the remote tip changed. Never force-push a shared branch. The merge is the one step an owner may not take alone. Step 4 gates it.
3. **Run owners in true parallel and never stack.** Use concurrent owners up to the Codex slot limit when PRs are self-contained: one writer per branch, disjoint files, cross-PR drift absorbed by rebase. Only genuinely overlapping work serializes. Self-contained PRs branch straight off the resolved trunk, and sequenced work is merge-then-branch. One exception: an owner that must split a genuinely dependent change may hold a short private base-branch stack.
4. **Swarm-verify every round before its merge.** A round starts at the owner's code-ready head SHA and at each later push that changes the PR's patch. At that SHA, run independent verifier lanes through the **swarm** skill in coverage mode and aggregate to one verdict. Use parallel lanes where isolated and within capacity; otherwise schedule them in waves. Each lane reports `PASS`, `ISSUES`, or `BLOCKED` with head/base SHAs and evidence paths. A clean verdict requires valid `PASS` evidence from every required lane, no unresolved proven findings, and no coverage gaps. The merge needs a clean verdict from the round whose patch matches the merge-ready head. Audit the receipts in the merge-ready report before the verdict. The lanes: re-run the gates at that SHA. Prove the load-bearing behavior live on the real surface the change touches (with the repository verification skill or the concrete driver established before the run). Audit the diff, distrusting the PR body. Run the audit as two or more review lanes with the full brief. Give each lane one main focus, such as consumer parity with trunk, lifetimes and races, or data and config safety. **Regression lane against trunk.** Run the same load-bearing scenario on current trunk. If trunk does not have the feature, record that fact and gate the behavior the diff adds plus the end state the user waits for instead of pretending trunk can produce it. The live lane is the floor, and a verdict without it is not clean. No merge without the root's clean verdict. When the lanes return, send every proven finding against the PR to the owner in one fix-forward. A defect that a lane filed as a note is a finding. For each behavior finding, ask for a red test that covers every site with the same defect. Where no test can show the defect, ask for a repro receipt instead. Add that defect to the next round's review brief. The new head gets a fresh swarm and a fresh verdict, except for lane results that stay valid under the patch-id rule in `shipping.md`.
5. **On a clean verdict the owner merges, and a fresh owner takes the next item.** The owner merges only from a head freshly rebased onto trunk. Merge prep never comes before a round's lanes start, and it ends with a rebase onto current trunk right before the merge. After the merge-prep rebase, the owner reports the new head SHA. CI must pass on that head before the merge, and the patch-id rule decides whether the round's verdict still holds. Once that head is green and its patch-id matches the verdict's under the patch-id rule in `shipping.md`, a later trunk move does not force another rebase. Right before the merge, fetch trunk and check that `git merge-tree` of the head against current trunk is clean. Also compare paths changed on trunk since the merge base with paths changed by the PR and paths controlling its CI. Use the resolved remote/trunk refs. Any overlap requires another rebase and verification check. If either check fails, rebase again, report the new head SHA, wait for CI to pass on it, and repeat these checks. A new head voids the verdict unless the patch-id is unchanged. Immediately before landing, read the current head and require passing required checks, satisfied review/queue requirements, and confirmed mergeability. Do not bypass branch protections or reuse a verdict for a different patch. The owner merges its own PR through the resolved forge using the repository's permitted merge method, preferring squash, and returns. A fresh owner picks up the next self-contained item from the queue, per pstack's Subagents section. The operator's full-autonomy grant plus the root's clean verdict is the merge authorization that babysitting alone never has. Operator-named items stop at merge-ready and wait for the operator's click.
6. **Run the root layer.** A genuinely new raise of a pinned gate or budget value (a limit CI only lets tighten) needs your fresh countersign, granted only after verifier proof. If the operator's grant or standing orders cover approvals, that countersign is the approval. The owner records it in the form that the tool's approval contract allows, with a pointer to the root's countersign. A lane checks the record against that countersign. The root never gives or bypasses an approval that the forge enforces. Absorbing values that already landed on trunk is drift, not a raise. Run the supervision loop below while the session is active.

   **Session supervision.** Record `next_audit_at` when the run starts. Process agent completions and forge changes as they arrive, using waits of at most 60 seconds. At least hourly, and before final handoff, audit every owner and child. Re-read the checked-in autopilot instructions used for this run; do not silently change protocol when trunk changes. Probe liveness and collect decision trails. Count commits, pushes, PR/check changes, and persisted evidence as progress, not promises. A lane that errors or exceeds its expected runtime without progress needs a liveness check; if stuck, stop it and replace it with the consolidated brief and exact revision.

   Confirm the old writer is stopped before granting its branch or checkout to a replacement. If stop cannot be confirmed, quarantine that writable location and report the block; never create competing writers. Preserve evidence and update `children.tsv` with owner/child IDs, expected runtime, last observed progress, and state. Do not classify the queue complete while descendants remain active. Sweep reviewer comments and audit evidence after batches of merges.

   On a session limit or interruption, send every owner and descendant a no-further-writes instruction and stop them using Codex controls. Persist a handoff outside product source containing queue order, mode and merge grant, PR URLs, branch/base/head SHAs, evidence/verdicts, pending CI or auto-merge, agent states, and the next action. Report any worker whose stop is unconfirmed. Report that supervision is inactive. Do not claim an hourly loop or autonomous service will keep running after the session ends. On resume, reconcile current forge/branch state before restarting owners or reusing verdicts.
7. **Stand down instantly on the operator's stop.** The operator's hold or stand-down reaches every owner as a zero-writes order immediately. Owners hold their briefs until the operator releases them.

**Reply:** the queue with each PR's owner, state, and head SHA. Each verdict and the swarm that produced it. What merged and what each fresh owner took next. Countersigns granted and why. Open operator gates. Where the collected decision trails live.
