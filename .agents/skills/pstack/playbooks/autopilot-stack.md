### Autopilot-stack

**You own the stack, never the landing. Build and verify the queue with full autonomy, then hand the operator one linear base-branch stack to review and land.** The sibling of **Autopilot-full**. Read [Autopilot-full](autopilot-full.md) for its verification prerequisites, owner records, round verification, and session supervision. This playbook overrides its merge behavior: no agent lands the stack.

1. **Run the owner loop unchanged.** Resolve the forge once for the program. Use the available Codex PR tools or authenticated repository forge CLI. Resolve the remote and trunk branch rather than assuming `main`. Follow PR registration and body-file rules in [Opening a PR](opening-a-pr.md) for every owner and every stack layer. One Codex owner agent per PR owns its change end to end: build, first push, an early PR opened before self-proof, self-proof (gates, CI, receipts), reviewer feedback triage per `../references/reviewer-feedback.md`, direct diff cleanup, comment review, and babysit to green per `babysit.md`. Owners parallelize within available Codex capacity when the work is self-contained. Reserve verifier capacity or schedule owners and lanes in waves. Within about 15 minutes, every owner starts a `decisions.tsv` trail per the **show-me-your-work** skill, pushes its first branch snapshot, and opens an early PR with its current verification status clearly stated, respecting an explicit draft preference. After that, the owner pushes its branch again after every verifiable unit (hooks on, a WIP commit is fine). Keep the trail uncommitted and return it in the report. Owners also keep the `children.tsv` of Autopilot-full step 2.
2. **Supervise in the active session.** Follow Autopilot-full step 6: audit at least hourly and on handoff, process completions with bounded waits, inspect real side effects, replace stuck workers only after stopping their writes, and track all children. On a session limit or interruption, stop workers, persist the queue/stack and evidence handoff, and report that supervision is inactive. No unattended scheduler is installed.
3. **Hold the operator gates.** State-then-wait, so a request to state the plan is not a go. On the operator's stop, every owner takes an immediate zero-writes hold.
4. **Verify each round.** The owner reports its code-ready head SHA once the shipped code is final, and STACK-READY with the exact head SHA when its loop is green. The root verifies each round per Autopilot-full step 4, with STACK-READY in place of merge-ready. Nothing enters the stack unverified.
5. **Append on a clean verdict, never ship.** No owner merges, arms auto-merge, or closes. A clean verdict appends the PR to the one linear base-branch stack, in verified order or an order the operator specified.
6. **Single writer on topology, parallel writers on builds.** Owners push only their own branches and report the tip, current base, and intended parent. The root is the only topology writer. Before rebasing or retargeting a child, pause its owner's writes and confirm the tip; return ownership only after recording the new head and base. To append a PR, fetch the intended parent, rebase the child branch onto that exact parent tip, capture the expected remote tip with `ls-remote`, push using `--force-with-lease=<ref>:<expected-sha>` only if it is unchanged, and set the PR base to the parent branch. Create or retarget through the selected PR tools or forge CLI, setting the parent branch as the child's base. Follow [Opening a PR](opening-a-pr.md) for registration of every layer. Only the root PR targets trunk. Never submit or register the chain through `gt`.
7. **Absorb drift at the root, then re-verify what moved.** The root fetches current trunk and rebases the chain from bottom to top. When a rebase surfaces conflicts in an owner's files, that owner fixes its own slice and the root pushes the result. A rebase rewrites every SHA above it and voids verdicts at the old SHAs. Apply the patch-equivalence rule in `shipping.md` at each verdict SHA. Anything that is no longer valid goes back through this playbook's step 4 before delivery. Re-run mergeability and CI after every rewritten push even when the patch remains equivalent. The countersign rule is unchanged from Autopilot-full. A genuinely new pin raises a stop for the root's fresh countersign. Absorbing drift of landed values is not a raise.
8. **Deliver the chain.** Before delivery, re-check every final parent-to-head patch after append/rebase operations using step 7; an earlier verdict before topology changes is insufficient. The deliverable is one linear chain of verified PRs, reviewable bottom-up in the resolved forge, every link carrying its verifier verdict in the PR body or a comment. The operator reviews and lands it bottom-up through `shipping.md`, one PR at a time. Never merge or arm a child while it still targets an unmerged parent. After the root lands, prepare the next child through Shipping step 4, including transplanting only its own commits after a squash merge, then retarget it to trunk and apply Shipping's patch-equivalence and verification checks before landing or arming that PR.

**Choosing between the autopilots.** Autopilot-full when the PRs are independent and landing authority is granted. Autopilot-stack when the operator wants review before landing, the work is sequenced or coupled, or merge authority is withheld.

**Reply:** links to the stack root and tip, a one-line verdict summary per link, and anything parked or excluded with the reason.
